As an iOS developer, you already know Xcode, provisioning profiles, and CocoaPods. React Native builds directly on that knowledge — the `ios/` folder is a full Xcode project, and every native dependency flows through CocoaPods. This document maps what you already know to how React Native uses these tools.

## The ios/ Folder Structure

When you run `npx react-native init MyApp`, the CLI generates an `ios/` directory with the following structure:

```
ios/
  MyApp/
    AppDelegate.mm          ← entry point, replaces your old AppDelegate.swift
    AppDelegate.h           ← header (Obj-C/C++ interop)
    Info.plist              ← bundle ID, display name, permissions — same as you know
    Images.xcassets/        ← launch screen assets
    LaunchScreen.storyboard ← launch screen
    main.m                  ← Obj-C main, initializes the AppDelegate
  MyApp.xcodeproj/          ← raw Xcode project — do NOT open this directly
  MyApp.xcworkspace/        ← workspace that includes Pods — ALWAYS open this
  Podfile                   ← your dependency manifest
  Podfile.lock              ← lockfile — commit this to git
  Pods/                     ← generated by pod install — do NOT commit this
```

The distinction between `.xcodeproj` and `.xcworkspace` is identical to any other CocoaPods project you've worked with. Opening `.xcodeproj` directly means Xcode can't find the `Pods` targets, and the build fails immediately. Treat `.xcworkspace` as the only entry point.

### AppDelegate.mm — Why the .mm Extension

React Native's `AppDelegate` is written in Objective-C++ (`.mm`), not Swift. This is because the React Native C++ runtime (JSI, Fabric, TurboModules) is exposed through C++ headers that cannot be imported directly from a pure Swift file. If you want to write Swift, do so inside your own view controllers and modules — the entry point stays in `.mm`.

The file extension is not a limitation to work around; it's a deliberate boundary. Your Swift code stays in Swift. The RN initialization code stays in `.mm`.

## CocoaPods' Role in React Native

The entire native layer of React Native is distributed as CocoaPods. The `react-native` npm package ships with a `React-Core.podspec` (and dozens of sub-specs). When you run `pod install`, CocoaPods resolves all those specs together with your own dependencies.

Every npm package that has a native iOS module ships with a `.podspec` at its root. Examples:

- `react-native-camera` → `RNCamera.podspec`
- `react-native-async-storage` → `RNCAsyncStorage.podspec`
- `react-native-reanimated` → `RNReanimated.podspec`

The React Native CLI automates registering these specs via the `use_native_modules!` helper in your Podfile. You don't add those pod lines manually — `use_native_modules!` scans `node_modules` and adds them automatically.

## Podfile Anatomy

A generated Podfile for a React Native 0.76 project looks like this:

```ruby
require_relative '../node_modules/react-native/scripts/react_native_pods'
require_relative '../node_modules/@react-native-community/cli-platform-ios/native_modules'

platform :ios, min_ios_version_supported
prepare_react_native_project!

linkage = ENV['USE_FRAMEWORKS']
if linkage != nil
  Pod::UI.puts "Enabling #{linkage}ly linked Frameworks"
  use_frameworks! :linkage => linkage.to_sym
end

target 'MyApp' do
  config = use_native_modules!

  use_react_native!(
    :path => config[:reactNativePath],
    :hermes_enabled => true,
    :fabric_enabled => true,
    :flipper_configuration => FlipperConfiguration.disabled,
    :app_path => "#{Pod::Config.instance.installation_root}/.."
  )

  post_install do |installer|
    react_native_post_install(
      installer,
      config[:reactNativePath],
      :mac_catalyst_enabled => false
    )
  end
end
```

### Key Entries

`platform :ios, min_ios_version_supported`
The `min_ios_version_supported` helper resolves to `14.0` in React Native 0.76. iOS 14 is the minimum because the Metal-backed Fabric renderer and JSI require APIs introduced in that version. Do not lower this value without understanding which RN APIs will break.

`use_native_modules!`
Scans `node_modules` for every package that has a `.podspec` and auto-links them. The returned `config` value carries the resolved path to the `react-native` package itself.

`use_react_native!`
A macro defined by React Native that adds all core pods: `React-Core`, `React-Fabric`, `React-jsi`, `React-hermes`, and others. The named arguments control the New Architecture flags:

| Argument | Effect |
|---|---|
| `:hermes_enabled => true` | Includes the `hermes-engine` pod, sets `RCT_NEW_ARCH_ENABLED` |
| `:fabric_enabled => true` | Enables the Fabric renderer for native components |
| `:flipper_configuration` | Pass `FlipperConfiguration.disabled` for production pipelines |

`post_install`
The `react_native_post_install` hook patches build settings on all pod targets — minimum deployment target, C++ standard library, linker flags. Do not remove it; builds will fail without it.

## pod install vs pod update

This mirrors standard CocoaPods practice with one React Native-specific nuance.

**pod install** resolves dependencies according to `Podfile.lock`. If `Podfile.lock` exists, every pod is pinned to the exact version already recorded. Run this command:
- after cloning the repository for the first time
- after adding or removing an npm package that has native code
- after any change to the `Podfile`
- after running `npm install` / `yarn` in CI

**pod update** ignores `Podfile.lock` and resolves the latest compatible version of each pod. Run this deliberately, not by default:
- when you want a newer version of a pod (e.g. after upgrading `react-native` itself)
- to update a single pod: `pod update RNReanimated`

**Commit strategy for Podfile.lock:** Always commit `Podfile.lock`. It's the equivalent of `yarn.lock` or `Package.resolved` — it pins the entire iOS dependency tree so every developer and every CI machine builds with exactly the same native code. Not committing means two developers running `pod install` on the same branch can get different pod versions, causing hard-to-diagnose build failures.

The `Pods/` directory itself should be in `.gitignore`. It is reproducible via `pod install` and often hundreds of megabytes.

## AppDelegate.mm for the New Architecture

With React Native 0.76, `AppDelegate.mm` uses `RCTAppDelegate` as its base class. This is the entry point where you signal to the runtime that your app uses New Architecture features.

```objc
#import "AppDelegate.h"
#import <React/RCTBundleURLProvider.h>

@implementation AppDelegate

- (BOOL)application:(UIApplication *)application
    didFinishLaunchingWithOptions:(NSDictionary *)launchOptions
{
  self.moduleName = @"MyApp";
  self.initialProps = @{};
  return [super application:application
      didFinishLaunchingWithOptions:launchOptions];
}

- (NSURL *)sourceURLForBridge:(RCTBridge *)bridge
{
  return [self bundleURL];
}

- (NSURL *)bundleURL
{
#if DEBUG
  return [[RCTBundleURLProvider sharedSettings]
      jsBundleURLForBundleRoot:@"index"];
#else
  return [[NSBundle mainBundle] URLForResource:@"main" withExtension:@"jsbundle"];
#endif
}

@end
```

`RCTAppDelegate` internally reads the New Architecture flags that were baked in at pod install time. You do not set `bridgelessEnabled`, `turboModuleEnabled`, or `fabricEnabled` manually in the generated code — those are controlled by Podfile macros and propagated through compiler preprocessor defines (`RCT_NEW_ARCH_ENABLED`).

**When you need to override:** If you are migrating a brownfield app or need to selectively disable a feature, you can override the property:

```objc
- (BOOL)fabricEnabled
{
  return YES; // explicit, equivalent to the default when RCT_NEW_ARCH_ENABLED=1
}
```

For brownfield integration, you may instantiate `RCTBridge` directly instead of using `RCTAppDelegate`. In that case you are responsible for configuring the bridge with a module registry that matches your Podfile flags. That pattern is covered in the Brownfield module.

## xcconfig and Environment Variables

React Native projects ship with Xcode configuration files generated by CocoaPods. After `pod install`, you'll see:

```
ios/
  Pods/
    Target Support Files/
      Pods-MyApp/
        Pods-MyApp.debug.xcconfig
        Pods-MyApp.release.xcconfig
```

These files are referenced automatically by your project's configurations. If you want to add your own build settings (e.g. a `BUILD_ENV` variable passed to `Info.plist`), the correct approach is to add a custom `.xcconfig` that includes the Pods one:

```
// ios/Config/Debug.xcconfig
#include "Pods/Target Support Files/Pods-MyApp/Pods-MyApp.debug.xcconfig"

BUILD_ENV = development
API_BASE_URL = https://api-dev.example.com
```

Then in `Info.plist`, reference the variable:

```xml
<key>APIBaseURL</key>
<string>$(API_BASE_URL)</string>
<key>BuildEnvironment</key>
<string>$(BUILD_ENV)</string>
```

In your Swift code, read it at runtime:

```swift
let apiBase = Bundle.main.object(forInfoDictionaryKey: "APIBaseURL") as? String ?? ""
```

Point each Xcode configuration (Debug, Release, Staging) to the corresponding `.xcconfig` file in the project settings under the "Info" tab. The Pods `.xcconfig` must always be included at the top — CocoaPods writes linker flags there, and omitting the include breaks the link phase.

## Schemes and Configurations

React Native generates two configurations by default: `Debug` and `Release`. This maps to what you already know from Xcode.

For a `Staging` environment, add a third configuration:

1. In Xcode, open the project file (not a target). Under "Info", duplicate "Release" and name it "Staging".
2. Create `ios/Config/Staging.xcconfig` (include `Pods-MyApp.release.xcconfig` because Staging uses release-mode optimizations but points at a staging backend).
3. Add a new scheme: Product > Scheme > New Scheme, name it `MyApp Staging`. Edit the scheme and change the Build Configuration for each action (Build, Run, Archive) to `Staging`.
4. In CI, pass `-scheme "MyApp Staging" -configuration Staging` to `xcodebuild`.

Configuration names matter: CocoaPods maps pod build configurations to your app's configurations by name. If you add "Staging" and CocoaPods doesn't know about it, you'll get missing `xcconfig` include warnings. Add a mapping in the Podfile:

```ruby
project 'MyApp', {
  'Debug' => :debug,
  'Release' => :release,
  'Staging' => :release
}
```

## Build Phases: Bundle React Native Code and Images

React Native adds a custom build phase script to your Xcode target called "Bundle React Native code and images". It is what invokes Metro during a Debug build and bundles JS for Release:

```bash
set -e

WITH_ENVIRONMENT="../node_modules/react-native/scripts/xcode/with-environment.sh"
REACT_NATIVE_XCODE="../node_modules/react-native/scripts/react-native-xcode.sh"

/bin/sh -c "$WITH_ENVIRONMENT $REACT_NATIVE_XCODE"
```

In `DEBUG` mode, this script starts the Metro bundle server (or connects to an already-running one). The app loads the JS bundle over HTTP from `localhost:8081`. This is why you see the Metro packager starting when you run the app from Xcode in debug mode.

In `RELEASE` mode, the script calls `react-native bundle` to produce a static `main.jsbundle` and copies it along with the asset catalog into the app bundle. The resulting IPA is self-contained — no Metro server needed.

Do not remove or reorder this build phase. It must run before the "Copy Bundle Resources" phase so that the generated `main.jsbundle` and `assets/` folder exist before Xcode tries to embed them.

## Swift Package Manager vs CocoaPods

As of React Native 0.76, CocoaPods is the required dependency manager for iOS. Swift Package Manager is not yet a first-class citizen for React Native's own dependencies.

The reasons are structural. React Native's CocoaPods integration uses custom Ruby helpers (`use_react_native!`, `react_native_post_install`) to propagate compiler flags, patch deployment targets, and configure the Hermes engine across dozens of sub-specs. SPM has no equivalent hook system.

**Current state:**
- React Native core pods: CocoaPods only
- Most community libraries: CocoaPods only (`.podspec`-based)
- Some pure-Swift utility libraries: SPM-compatible, but if they have no RN native module they don't interact with CocoaPods at all

**Hybrid approach:** You can use SPM for your own pure-Swift libraries (analytics, design system components written in Swift) alongside CocoaPods for RN dependencies. Add SPM packages through File > Add Packages in Xcode as normal. The two systems don't conflict as long as the SPM packages don't need to expose themselves to the JavaScript layer.

**What's coming:** The React Native team has signaled SPM support as a goal for a future major version. Some community members maintain SPM-compatible forks of popular libraries. For production projects today, treat CocoaPods as the only supported path for anything that bridges to JavaScript.

## Common Xcode Errors and Fixes

### "Undefined symbol: _OBJC_CLASS_$_RCTBridge"

This means the linker can't find React Native symbols. Almost always caused by one of:

- Opening `.xcodeproj` instead of `.xcworkspace`. Close Xcode, open the workspace file.
- Missing `pod install` after adding a new dependency. Run `pod install` and clean the build folder (Product > Clean Build Folder, or `Shift+Cmd+K`).
- Mismatch between the `react-native` npm version and the pod version. Delete `Pods/` and `Podfile.lock`, run `pod install` again.

### "No podspec found for 'SomePod'"

A library registered itself in `use_native_modules!` but its `.podspec` references a file or dependency that doesn't exist.

Diagnostic steps:
1. Verify you ran `npm install` before `pod install`.
2. Read the `.podspec` at the root of the problematic npm package. Look for a `dependency` or `source_files` that points to a path that doesn't exist.
3. Check the library's GitHub issues — it's often a version mismatch requiring a specific npm version of the library.

### Build Fails After Changing Podfile Flags

If you toggle `:hermes_enabled` or `:fabric_enabled` in the Podfile, you must run a full clean cycle:

```bash
cd ios
rm -rf Pods Podfile.lock
pod install
```

Then in Xcode: Product > Clean Build Folder. Also delete DerivedData:

```bash
rm -rf ~/Library/Developer/Xcode/DerivedData
```

DerivedData caches compiled pod targets. If you change compiler defines (like `RCT_NEW_ARCH_ENABLED`) without clearing DerivedData, Xcode may link a cached binary built with the old defines, producing subtle runtime crashes instead of build errors.

### "The iOS Simulator deployment target is set to X.Y, but the range of supported deployment targets is Y.Z to A.B"

This happens when `react_native_post_install` was not applied, or when a pod has an older minimum deployment target than your project. The post-install hook patches all pod targets to match the value set in `platform :ios`. If you see this warning after the hook is present, it usually means a pod has an explicit minimum that CocoaPods can't override. Report it to that library's maintainer, or add a manual override in `post_install`:

```ruby
post_install do |installer|
  react_native_post_install(installer, config[:reactNativePath])
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '14.0'
    end
  end
end
```

### "Command PhaseScriptExecution failed with a nonzero exit code" on the Bundle Phase

The Metro bundle phase failed. Run the equivalent command manually in the terminal to see the actual error:

```bash
cd ios
NODE_BINARY=$(command -v node) \
  ../node_modules/.bin/react-native bundle \
  --entry-file index.js \
  --platform ios \
  --dev false \
  --bundle-output /tmp/main.jsbundle \
  --assets-dest /tmp/assets
```

Common causes: Metro can't resolve a module (missing `npm install`), a Babel plugin is misconfigured, or `node` is not in the PATH that Xcode sees (fix: set `NODE_BINARY` in the bundle phase script or use `.xcode.env` to export the correct PATH).

## Summary

Your iOS knowledge transfers directly. The `ios/` folder is a real Xcode project. CocoaPods manages all native dependencies — both React Native's own internals and community libraries. The Podfile controls New Architecture flags, and `Podfile.lock` must be committed. AppDelegate.mm stays in Objective-C++ by design. Environment-specific configuration flows through scheme-inherited `.xcconfig` files. Build failures almost always fall into three categories: wrong file opened, missing pod install, or stale DerivedData.
